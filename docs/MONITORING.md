# Моніторинг і сповіщення

Версія: 1.0 · 2026-08-12

Модуль відповідає на просте питання: **чи все гаразд із парком пристроїв** —
і повідомляє, коли ні. Усе, на що він спирається, — технічні показники стану
самих пристроїв.

---

## 1. Що збирається (і що ні)

| Показник | Джерело на пристрої |
|---|---|
| Онлайн / офлайн | час останнього звернення агента (`last_seen_at`) |
| Заряд, стан живлення, здоровʼя й температура батареї | `ACTION_BATTERY_CHANGED` |
| Оперативна памʼять (всього / доступно) | `ActivityManager.MemoryInfo` |
| Сховище (всього / вільно) | `StatFs` розділу даних |
| CPU: ядра, ABI, навантаження | `/proc/stat` (два зрізи), запасний варіант — `/proc/loadavg` |
| Час роботи | `SystemClock.elapsedRealtime()` |
| Версія Android, SDK, патч безпеки, ядро, build id | `android.os.Build` |
| Версія агента | `BuildConfig` |
| Тип підключення | `ConnectivityManager` (wifi / cellular / ethernet / vpn) |
| Версії застосунків | інвентар `PackageManager` (модуль застосунків) |
| Стан звітування геолокації | налаштування модуля + час останньої координати |
| Стан реєстрації | `devices.status` |

**Чого агент не збирає заради моніторингу:** назви Wi-Fi мережі (SSID),
оператора звʼязку, переліку процесів, історії використання застосунків,
буфера обміну, вмісту сповіщень. Жодне з цих значень не потрібне для
перелічених індикаторів, тож його просто немає в запиті.

Телеметрія надходить приблизно раз на хвилину (інтервал диктує сервер у
відповіді `next_report_seconds`) і **не пишеться в аудит** — інакше журнал
адміністративних дій потонув би в шумі. У журнал потрапляють похідні події:
відкриття й закриття сповіщень, зміни правил.

---

## 2. Правила

Правило = тип + пороги + важливість + область дії + пауза.

| Тип | Пороги (за замовчуванням) | Коли спрацьовує |
|---|---|---|
| `DEVICE_OFFLINE` | `offline_minutes` (30) | немає звʼязку довше за поріг |
| `LOW_BATTERY` | `battery_percent` (20), `ignore_when_charging` (так) | заряд ≤ порога |
| `LOW_STORAGE` | `free_percent` (10) або `free_mb` | лишилось менше вільного місця |
| `LOW_MEMORY` | `free_percent` (10) | мало доступної RAM |
| `HIGH_CPU` | `load_percent` (90) | навантаження ≥ порога |
| `OUTDATED_AGENT` | `min_version` | версія агента менша за мінімальну |
| `OUTDATED_ANDROID` | `min_sdk` (26) | SDK пристрою нижчий |
| `OUTDATED_APP` | `packages` (усі) | у репозиторії є новіша версія встановленого пакета |
| `LOCATION_REPORTING_STOPPED` | `silent_minutes` (180) | модуль увімкнено, але координат немає / дозвіл відкликано |
| `COMMAND_FAILURES` | `count` (3), `window_minutes` (60) | стільки невдалих команд за вікно |
| `ENROLLMENT_STATUS` | `states` (`suspended`, `pending`) | пристрій у небажаному стані реєстрації |

Пороги валідуються за типом правила: невідомий ключ або значення поза межами
(наприклад, `battery_percent: 150`) правило не збережуть. Область — усі
пристрої або один конкретний (`device_id`).

Довідник порогів для форми в панелі віддає `GET /alert-rules/schema`.

## 3. Життєвий цикл сповіщення

```
правило + пристрій ──► знахідки (0..N, кожна зі своїм dedup_key)
        │
        ├─ знахідка без активного алерта  ──► firing   + audit ALERT_RAISED   + WS
        ├─ знахідка з активним алертом    ──► оновлення message/last_seen_at
        └─ активний алерт без знахідки    ──► resolved + audit ALERT_RESOLVED + WS
```

* `dedup_key` не дає плодити дублікати: для `OUTDATED_APP` він включає імʼя
  пакета, тож кожен застарілий застосунок — окреме сповіщення.
* `cooldown_seconds` (типово година) стримує «миготіння»: після закриття той
  самий ключ мовчить задану паузу. `0` — відкривати одразу, щойно проблема
  повернулась.
* Оператор може **підтвердити** сповіщення (воно лишається відкритим, але
  позначеним) або **закрити** вручну. Якщо причина не зникла, наступна оцінка
  відкриє його знову.

### Коли відбувається оцінка

1. **Одразу після телеметрії** — пристрій надіслав зріз, правила для нього
   переоцінюються в тому ж запиті (звідси `alerts_raised` у відповіді).
2. **Щохвилини у фоні** ([`monitoring_loop`](../backend/app/services/monitoring_loop.py)) —
   ловить те, що не супроводжується запитом: насамперед «пристрій зник».
3. **Вручну** — `POST /monitoring/evaluate` (потрібен дозвіл `alert:manage`).

## 5. Живі оновлення

`WS /ws/admin?token=<access-JWT>` — канал **лише для читання**: повідомлення
від клієнта ігноруються, тож через сокет не можна виконати жодної дії в обхід
REST і RBAC. Підключення вимагає дозволу `device:read`; події розходяться між
репліками API через Redis pub/sub.

Типи подій: `alert_raised`, `alert_resolved`, `command_acked`,
`command_progress`, `command_completed`.

Панель використовує сокет як прискорювач: якщо він недоступний, сторінки
далі оновлюються за таймером, а перепідключення йде з наростаючою паузою.

## 6. Індикатори в панелі

* **Сторінка «Моніторинг»** — плитки (пристроїв / онлайн / офлайн / активних
  сповіщень / критичних / правил), перелік сповіщень із фільтром за станом і
  діями, вкладка правил із формою створення (пороги підставляються з
  довідника).
* **Список пристроїв** — колонки «Ресурси» (диск / RAM / CPU) і «Сповіщення»
  з бейджем найгіршої важливості.
* Стан звітування геолокації рахується як `active` / `blocked` / `disabled` —
  «увімкнено, але дозвіл відкликано» видно окремо.

---

## 7. Аудит

| Дія | Коли |
|---|---|
| `ALERT_RULE_CREATED` / `ALERT_RULE_UPDATED` / `ALERT_RULE_DELETED` | зміни правил (з порогами «було → стало») |
| `ALERT_RAISED` | відкрито сповіщення (актор — `system`, у деталях правило, пристрій, значення) |
| `ALERT_RESOLVED` | закрито автоматично (`auto: true`) або вручну (`auto: false`) |
| `ALERT_ACKNOWLEDGED` | оператор підтвердив |

---

## 8. Обмеження цієї версії

- Канали доставки — лише панель і WebSocket: пошти, Telegram чи webhook ще
  немає (структура правила готова прийняти поле `notify`).
- Немає придушення за розкладом (maintenance window) і групування схожих
  сповіщень у дайджест.
- Історія телеметрії зберігається, але графіків у панелі поки немає —
  показується лише поточний зріз.
- `/proc/stat` на частині пристроїв закритий; тоді навантаження CPU
  визначається з `/proc/loadavg`, а якщо і він недоступний — показник
  відсутній, і правило `HIGH_CPU` для такого пристрою просто не спрацьовує.
