# Звіт аудиту безпеки Fleet MDM

Дата: 2026-08-13 · Обсяг: бекенд (FastAPI), Android-агент, веб-панель,
інфраструктура (Docker, nginx, PostgreSQL, Redis).

Перевірено: автентифікація, авторизація, JWT, refresh-токени, облікові дані
пристроїв, enrollment, API, WebSocket, вивантаження/завантаження файлів,
APK, виконання команд, SQL, XSS, CSRF, SSRF, обхід шляхів, обмеження частоти,
керування секретами, конфігурація Docker, права БД, TLS.

**Підсумок:** знайдено 5 проблем високої та 17 середньої критичності.
Усі виправлені. Нижче — що саме було не так, чому це небезпечно і що зроблено.

---

## Високий рівень

### H1. Ін'єкція команд оболонки в привілейованих файлових операціях

`FileManager.runShell()` збирав команду підстановкою шляху в рядок і виконував
її через `su`:

```kotlin
runShell("rm $flags \"${target.absolutePath}\"")   // було
```

Шлях приходить із сервера в payload команди. Серверна нормалізація
(`file_paths.normalize_path`) відхиляла `..`, керуючі символи й зворотні
слеші, але **пропускала** `"`, `` ` ``, `$`, `;`, `&`, `|`. Шлях виду

```
/allowed/dir/x"; rm -rf /data; echo "
```

проходив усі перевірки й перетворювався на довільну команду з правами root
на пристрої — у будь-якому каталозі з `allow_privileged`.

**Виправлено на трьох рівнях:**

1. Сервер (`app/services/file_paths.py`) відхиляє метасимволи оболонки й
   керуючі символи напрямку тексту в кожному елементі шляху; спроба
   потрапляє в аудит як `FILE_ACCESS_DENIED`.
2. Агент (`FilePathGuard.rejectShellMetacharacters`) перевіряє те саме
   самостійно — він не покладається на сервер наосліп.
3. `runShell` більше не приймає готовий рядок: тільки назву утиліти з
   фіксованого переліку (`ls`, `mkdir`, `mv`, `rm`) та окремі аргументи,
   які екрануються `shellQuote` перед склеюванням.

### H2. Ін'єкція команд через контрольну суму APK

`ApkInstaller.installViaRoot()` підставляв у `su -c "pm install -r \"…\""`
шлях, ім'я якого будувалося з `sha256` із payload команди без перевірки
формату. Рядок `a";reboot;#` давав виконання довільної команди.

**Виправлено:** `FilePathGuard.requireSha256()` приймає лише 64 шістнадцяткові
символи; шлях додатково екранується `shellQuote`.

### H3. Вихід за межі каталогу при завантаженні APK

Той самий неперевірений `sha256` використовувався як ім'я файла в кеші:
`File(cacheDir, "${expectedSha256.take(16)}.apk")`. Значення на кшталт
`../../databases/x` писало файл поза каталогом кешу агента.

**Виправлено:** ім'я будується лише після `requireSha256()`.

### H4. `docker-compose.override.yml` тихо знижував безпеку робочого сервера

Файл із такою назвою `docker compose up` підхоплює **автоматично**. Він
виставляв `APP_ENV=development` (а з ним вимикав усю перевірку секретів у
`Settings._validate_secrets`), запускав uvicorn з `--reload`, монтував
вихідний код у контейнер, публікував API на `0.0.0.0:8000` в обхід nginx і
TLS та вимикав nginx через профіль.

**Виправлено:** файл перейменовано на `docker-compose.dev.yml` і підключається
лише явно (`make up-dev`). Порти прив'язані до `127.0.0.1`. У самому файлі —
пояснення, чому назва саме така.

### H5. Redis без автентифікації

У Redis лежать nonce автентифікації пристроїв, лічильники обмеження частоти
й **канали доставки команд**. Публікація в `device:<uuid>` рівносильна
виконанню довільної команди на пристрої (зокрема `FILE_DELETE`,
`APP_INSTALL`). Доступ був відкритий будь-кому в мережі Docker, а в режимі
розробки — ще й на опублікованому порту.

**Виправлено:** `requirepass` обов'язковий (`REDIS_PASSWORD`), `CONFIG`,
`FLUSHALL`, `FLUSHDB`, `DEBUG` перейменовані у порожні імена. У production
`Settings` не стартує, якщо в `REDIS_URL` немає пароля.

## Середній рівень

### M1. Access-токени не відкликалися

Вихід, зміна пароля чи ролі анулювали лише refresh-токени. Виданий
access-JWT лишався дійсним до 15 хвилин — зокрема викрадений.

**Виправлено:** `users.sessions_valid_from` і `devices.tokens_valid_from`.
Токен, виданий раніше цієї мітки, не приймається — ані в REST, ані в
WebSocket. Мітка зсувається при виході, `logout-all`, зміні пароля, зміні
ролі, деактивації, призупиненні/видаленні пристрою й ротації ключа.
Для точного порівняння в токен додано `iat_ms` (посекундного `iat` не
вистачало, щоб відкликати токен, виданий у ту саму секунду).

### M2. Refresh-токен у `localStorage`

14-денний токен лежав у сховищі, доступному будь-якому скрипту: одна
XSS-вразливість — і сесія викрадена надовго.

**Виправлено:** refresh-токен віддається лише cookie
`HttpOnly; Secure; SameSite=strict; Path=/api/v1/auth` і в тілі відповіді
більше не повертається. У `localStorage` лишився прапорець «сесія була».
Оскільки автентифікація на цих ендпоїнтах тепер cookie-based, додано захист
CSRF за схемою double-submit (`X-CSRF-Token` + cookie).

### M3. Відсутність Content-Security-Policy

Ні бекенд, ні nginx не надсилали CSP; не було `Cross-Origin-Resource-Policy`,
`X-Permitted-Cross-Domain-Policies`, а відповіді API кешувалися за
замовчуванням.

**Виправлено:** CSP без `unsafe-inline` для скриптів, повний набір заголовків
у `app/core/middleware.py` і продубльований у nginx (і в периметровому, і в
контейнері панелі). Усі відповіді API — `Cache-Control: no-store`.

### M4. Застаріла авторизація в WebSocket підтримки

`_run_viewer` читав `row.input_enabled` один раз при підключенні. Оператор,
у якого адміністратор уже вимкнув керування (або чий сеанс завершив
користувач пристрою), продовжував надсилати події вводу до кінця з'єднання.

**Виправлено:** стан сеансу й права оператора перечитуються з БД (кеш 2 с)
перед кожним керуючим повідомленням; втрата прав закриває сокет. Додано
стелю розміру керуючого кадру й фільтр параметрів якості.

### M5. Гонка при використанні enrollment-токена

`token.use_count += 1` за схемою «прочитали-додали-записали»: кілька
одночасних запитів обходили `max_uses`.

**Виправлено:** рядок береться `SELECT … FOR UPDATE` (крім SQLite), а саме
використання «займається» умовним `UPDATE … WHERE use_count < max_uses` з
перевіркою `rowcount`. Рішення ухвалює БД, а не прочитане раніше значення.

### M6. Агент надсилав свій токен на будь-який URL із команди

`download_url`, `status_url`, `chunk_url`, `content_url` бралися з payload і
використовувалися разом із Bearer-токеном пристрою без перевірки хоста.

**Виправлено:** `ServerUrlGuard` звіряє схему, хост і порт із адресою,
отриманою під час enrollment; пониження https→http і облікові дані в URL
відхиляються.

### M7. Облікові дані пристрою не можна було змінити

Ключ, виданий при реєстрації, жив вічно; підозра на компрометацію означала
повне перереєстрування пристрою.

**Виправлено:** повноцінна ротація — див. розділ 2.4 у `SECURITY.md`.

### M8. Токени WebSocket осідали в логах nginx

Браузерний WebSocket не вміє задавати `Authorization`, тож токен передається
параметром URL, а `log_format` писав `$request_uri` — разом із токеном.

**Виправлено:** у журнал іде `$uri` (лише шлях).

### M9. Застосунок працював у БД роллю-власником схеми

Помилка або ін'єкція в коді могли б призвести до `DROP TABLE`.

**Виправлено:** `infra/postgres/init/01-app-role.sh` створює роль
`fleet_app` з `SELECT/INSERT/UPDATE/DELETE` і без права створювати об'єкти;
міграції виконуються окремо роллю-власником (`MIGRATION_DATABASE_URL`).

### M10. Агент міг звітувати довільний прогрес передачі

`transfer.received_bytes = payload.received_bytes` без перевірок.

**Виправлено:** приймається лише монотонне зростання в межах оголошеного
розміру.

### M11. APK: відсутність політики підпису й ризик «zip-бомби»

Схеми підпису лише детектувалися, але непідписаний пакет приймався;
сертифікат читався без обмеження розміру.

**Виправлено:** непідписані APK відхиляються на межі приймання (з аудитом);
додано `APK_ALLOWED_SIGNERS` для закріплення власного сертифіката збірки;
парсер обмежує кількість записів, коефіцієнт стиснення й розмір сертифіката,
відхиляє записи з абсолютними шляхами та `..`.

### M12. Відсутність обмеження розміру тіла на рівні застосунку

`client_max_body_size 512m` діяв на всі маршрути, включно з `/auth/login`.

**Виправлено:** `RequestGuardMiddleware` обмежує звичайні запити
(`MAX_JSON_BODY_KB`, типово 512 КБ) і перевіряє `Content-Type`; великі тіла
дозволені лише на потокових маршрутах. У nginx стеля за замовчуванням
знижена до 1 МБ і піднімається точково для вивантажень.

### M13. `/health` розкривав версію й склад залежностей без автентифікації

**Виправлено:** у production публічний `/health` віддає лише статус; повна
картина — на `/health/details` за дозволом `settings:manage`.

### M14. Контейнери без базового загартування

**Виправлено:** `no-new-privileges`, `cap_drop: [ALL]`, `read_only` з tmpfs
для API.

### M15. Надто широкий CORS

`allow_methods=["*"]`, `allow_headers=["*"]` разом із `allow_credentials=True`.

**Виправлено:** явні переліки методів і заголовків; у production
забороняються `*` у `CORS_ORIGINS` і джерела на http. Додано
`TrustedHostMiddleware` (`ALLOWED_HOSTS`).

### M16. Не було механізму ротації серверних секретів

Зміна `JWT_SECRET` або `TOKEN_HASH_SECRET` розлогінювала всіх і ламала
пошук збережених enrollment-токенів.

**Виправлено:** `*_PREVIOUS` для обох секретів — підписуємо новим, приймаємо
й старе; `TOKEN_EPOCH` для аварійного відкликання всього одразу; стан і
процедура — `GET /api/v1/maintenance/secrets`.

### M17. Обмеження частоти покривало лише вхід, enrollment і авторизацію агента

**Виправлено:** глобальний адаптивний ліміт на весь `api_router` (окремі
кошики для читання й змін), ідентифікація за суб'єктом токена, а не лише за
IP; окремі ліміти для вивантажень, звітів агента, зміни пароля, оновлення
токена й ротації ключа. Периметровий ліміт додано в nginx.

## Перевірено — вразливостей не знайдено

| Область | Висновок |
|---|---|
| SQL-ін'єкції | Уся робота з БД — через SQLAlchemy з параметрами; сирого SQL немає, крім `SELECT 1` у health-check. |
| XSS | React екранує за замовчуванням; `dangerouslySetInnerHTML`, `innerHTML`, `eval` у коді панелі відсутні. CSP додано як другий рубіж. |
| SSRF на сервері | Бекенд не робить вихідних HTTP-запитів за адресами з даних користувача. (Аналогічну проблему на боці агента усунуто — M6.) |
| Обхід шляхів у сховищі | Імена артефактів будуються з SHA-256, ім'я вивантаження санітизується (`sanitize_filename`). |
| Розкриття існування облікових записів | Вхід повертає однакову помилку для невідомої пошти й невірного пароля. |
| Ключі пристроїв | Приватна частина ніколи не залишає Android Keystore; сервер зберігає лише публічний ключ. |

## Що навмисно не змінювалося

Аудит не послабив жодного наявного контролю. Зокрема лишилися незмінними:

- **Згода користувача на показ екрана.** Сеанс підтримки не стає активним
  без явного `granted=true` від агента; системний індикатор
  `MediaProjection` не обходиться.
- **Видимість агента.** Іконка в лаунчері, постійне сповіщення, екран статусу.
- **Геолокація — opt-in.** Вимкнена при реєстрації, вмикається окремо й з аудитом.
- **Allowlist каталогів.** Порожній перелік = файловий модуль вимкнений.
- **`su` як запасний механізм.** Лишається вимкненим за замовчуванням і
  завжди повідомляється серверу в полі `mechanism`; ми його не розширювали,
  а лише зробили безпечним для аргументів.
