# Модуль керування файлами

Версія: 1.0 · 2026-08-12 · відповідає Milestone 5 (файлова частина)

Доступ до файлів пристрою обмежений **явно налаштованим переліком
каталогів**. Поза цим переліком модуль не працює — ні для адміністратора,
ні для агента.

---

## 1. Модель доступу

```
адміністратор ──► file_roots (allowlist для КОНКРЕТНОГО пристрою)
                     │
                     ├─ path              абсолютний нормалізований шлях
                     ├─ writable          читання / читання+запис
                     ├─ max_file_size_mb  ліміт на файл (поверх глобального)
                     └─ allow_privileged  чи можна su в цьому каталозі
```

| Умова | Наслідок |
|---|---|
| Для пристрою немає жодного `file_root` | Файловий модуль вимкнено: будь-яка операція → `403`, аудит `no_roots_configured` |
| Шлях поза allowlist | `403`, аудит `outside_allowlist` |
| Шлях містить `..` | `403`, аудит із текстом порушення; `..` **не розгортається**, а відхиляється |
| Запис у каталог `writable=false` | `403`, аудит `read_only_root` |
| Спроба видалити сам корінь allowlist | `409` |

Перевірка виконується **двічі**:

1. на сервері — [`file_paths.py`](../backend/app/services/file_paths.py) +
   [`files.py:authorize_path`](../backend/app/services/files.py);
2. на пристрої — [`FilePathGuard`](../android/app/src/main/java/ua/fleet/agent/files/FilePathGuard.kt),
   який канонізує шлях (`canonicalPath`) і повторно звіряє його з переліком,
   отриманим із сервера. Саме канонізація закриває обхід через **символьні
   посилання**: симлінк усередині дозволеного каталогу, що веде назовні,
   доступу не дає (тест `симлінк за межі allowlist не дає доступу`).

Крім того, у переліку каталогу приховуються записи, чий канонічний шлях
виходить за межі кореня.

### Чого модуль не робить

- не читає дані інших застосунків (`/data/data/<пакет>`) — такі шляхи просто
  неможливо додати «випадково»: їх треба явно внести в allowlist, і це
  фіксується в аудиті з іменем адміністратора;
- не витягує облікові дані, профілі браузерів, cookie чи токени сесій;
- не обходить пісочницю Android: усе, що агент бачить, — це те, що йому
  дозволяє ОС для свого UID (плюс `su` там, де адміністратор це явно ввімкнув
  для конкретного каталогу керування).

## 2. Операції

| Операція | Ендпоїнт | Дозвіл | Як виконується |
|---|---|---|---|
| Перелік каталогу | `POST /devices/{id}/files/list` | `file:read` | команда `FILE_LIST`, результат у `command.result.entries` |
| Створити каталог | `POST /devices/{id}/files/mkdir` | `file:write` | команда `FILE_MKDIR` |
| Перейменувати | `POST /devices/{id}/files/rename` | `file:write` | команда `FILE_RENAME` (у межах того самого каталогу) |
| Видалити | `POST /devices/{id}/files/delete` | `file:write` | команда `FILE_DELETE` (`recursive` для каталогів) |
| Отримати файл | `POST /devices/{id}/files/download` | `file:read` | передача + команда `FILE_DOWNLOAD` |
| Покласти файл | `POST /devices/{id}/files/upload` | `file:write` | передача + команда `FILE_UPLOAD` |

Метадані запису: імʼя, шлях, тип, розмір, час зміни, права (`rw-`), ознака
символьного посилання, доступність для читання й запису.

## 3. Передачі з відновленням

### З пристрою на сервер (`direction=download`)

```
адмін → POST /files/download {path}         створює transfer + команду
агент → GET  /device/files/transfers/{id}   ← received_bytes (звідки продовжити)
агент → POST /device/files/transfers/{id}/chunk   заголовок X-Chunk-Offset
        (повторюється, поки файл не закінчиться)
агент → POST /device/files/transfers/{id}/complete {sha256, size_bytes}
адмін → GET  /devices/{id}/files/transfers/{tid}/content
```

* Сервер дописує чанк **лише** з поточного кінця файла. Якщо агент надішле
  той самий зсув удруге — `409` із фактичним зсувом у повідомленні, тож
  дублювання даних неможливе.
* Ліміт розміру перевіряється на кожному чанку: перевищення → `422`,
  передача позначається `failed`, недописаний файл видаляється.
* `sha256` рахується сервером наново і звіряється з тим, що надіслав агент.
  Розбіжність → `failed`, файл видаляється, в аудиті `result=failure`.

### Із сервера на пристрій (`direction=upload`)

```
адмін → POST /files/upload (multipart)      сервер рахує sha256 і розмір
агент → GET  /device/files/transfers/{id}/content   із заголовком Range
        (після обриву — Range: bytes=<уже отримано>-)
агент → POST .../progress {received_bytes}  для індикатора в панелі
агент → POST .../complete {sha256}          звіряння суми
```

* Ендпоїнт вмісту підтримує `Range`, повертає `206 Partial Content` із
  `Content-Range`, а на некоректний діапазон — `416`.
* Агент пише у файл `<цільове імʼя>.fleetpart` поруч із метою і **перейменовує
  його лише після збігу контрольної суми**; при розбіжності частковий файл
  видаляється, а серверу надсилається `fail`.

## 4. Привілейований (root) доступ

Для рутованих пристроїв `su` дозволено **тільки** якщо каталог позначено
`allow_privileged=true`, і тільки як запасний шлях, коли звичайних прав
застосунку не вистачило. Використаний механізм завжди повертається серверу в
`result.mechanism` (`app` або `su`) і зберігається в історії операцій.

Це навмисно вузька щілина: прапорець ставиться на конкретний каталог
керування пристроєм, а не «на пристрій загалом».

## 5. Ліміти й TLS

| Параметр | Змінна | Типове значення |
|---|---|---|
| Максимальний файл | `MAX_FILE_TRANSFER_MB` | 256 МБ |
| Ліміт на каталог | `file_roots.max_file_size_mb` | не задано (діє глобальний) |
| Розмір чанка | `FILE_TRANSFER_CHUNK_KB` | 1024 КБ |
| Час життя передачі | `FILE_TRANSFER_TTL_SECONDS` | 24 год |

Ефективний ліміт = `min(ліміт каталогу, глобальний ліміт)`.

Увесь трафік іде через TLS-термінацію nginx (`infra/nginx/nginx.conf`);
`client_max_body_size` синхронізовано з лімітом вивантаження. Агент
використовує `network_security_config` без `trustAll`.

## 6. Аудит

| Дія | Коли |
|---|---|
| `FILE_ROOT_CHANGED` | додано/прибрано дозволений каталог (з режимом і лімітами) |
| `FILE_LIST` | запит переліку каталогу |
| `FILE_MKDIR`, `FILE_RENAME`, `FILE_DELETE` | відповідні операції (зі шляхами «звідки → куди») |
| `FILE_UPLOAD` | адміністратор поклав файл (розмір, sha256, цільовий шлях) |
| `FILE_DOWNLOAD` | запит файла (`phase=requested`) і фактичне вивантаження адміністратором (`phase=fetched_by_admin`) |
| `FILE_TRANSFER_COMPLETED` | результат від пристрою: успіх або помилка з причиною |
| `FILE_ACCESS_DENIED` | будь-яка відмова: `no_roots_configured`, `outside_allowlist`, `read_only_root`, порушення формату шляху — разом із повним шляхом, який намагалися відкрити |

## 7. Що перевірено тестами

`backend/tests/test_file_paths.py` (30 тестів) — нормалізація й межі:
traversal, зворотні слеші, NUL-байт, довжини, схожі префікси
(`/sdcard/Fleet` vs `/sdcard/FleetPrivate`).

`backend/tests/test_files.py` (28 тестів) — поведінка API: allowlist,
read-only, ліміти розміру, повний цикл обох напрямів, відновлення після
обриву, дублювання зсуву, розбіжність контрольної суми, ізоляція між
пристроями, RBAC (`operator` читає, `admin` пише, `auditor` не має доступу),
анонімний доступ.

`android/app/src/test/.../FilePathGuardTest.kt` (10 тестів) — локальний
guard, у тому числі симлінк за межі allowlist.

## 8. Обмеження цієї версії

- Переміщення між каталогами не підтримується — лише перейменування в межах
  поточного каталогу (простіше перевіряти й аудитувати).
- Немає докачки для *вивантаження адміністратором* готового файла з сервера
  (це звичайний `FileResponse`); відновлення реалізоване саме на ділянці
  «сервер ↔ пристрій», де обриви ймовірні.
- Перелік каталогу не пагінується: дуже великі каталоги (десятки тисяч
  записів) варто розбивати підкаталогами.
- Прострочені передачі прибираються ретеншном разом з іншими даними; окремого
  «збирача сміття» для незавершених файлів у сховищі поки немає.
