# Модуль геолокації

Версія: 1.0 · 2026-08-12 · відповідає Milestone 6

Геолокація — **окремий opt-in модуль**. Він вимкнений доти, доки
адміністратор не увімкне його явно для конкретного пристрою, і працює лише
доки користувач пристрою тримає наданий дозвіл Android.

---

## 1. Чотири умови збору

Координата збирається тільки якщо виконані **всі** чотири умови:

| # | Умова | Де перевіряється |
|---|---|---|
| 1 | Адміністратор увімкнув модуль для цього пристрою | сервер: `location_settings.enabled`; агент: локальна копія конфігу |
| 2 | Користувач надав дозвіл Android і геолокація ввімкнена в системі | `LocationPermissions.current()` на пристрої |
| 3 | Політика батареї дозволяє | `BatteryPolicy.shouldCollect()` |
| 4 | Настав час чергового виміру | інтервал із конфігурації |

Навіть якщо агент помилково спробує надіслати координати при вимкненому
модулі, **сервер їх не збереже**: `POST /device/location` поверне `403` і
запише `LOCATION_UPLOAD_REJECTED` з `result=denied`. Агент, отримавши 403,
вимикає модуль локально й очищає чергу.

### Чого модуль не робить

- не обходить діалоги дозволів і не використовує «сірих» способів отримати
  координати (Wi-Fi-сканування, IMSI, читання чужих застосунків);
- не збирає координати «про запас», коли модуль вимкнено;
- не приховує факт збору: у сповіщенні агента написано, що геолокація
  увімкнена, а на екрані показано інтервал, точність і час останнього виміру.

## 2. Життєвий цикл конфігурації

```
адмін → PUT /devices/{id}/location/settings {enabled, interval, accuracy, distance}
   │
   ├─ diff «було → стало» ──▶ audit LOCATION_CONFIG_CHANGED (або LOCATION_DISABLED)
   ├─ consent_recorded_at = now (при вмиканні)
   └─ команда LOCATION_CONFIG ──Redis/WS──▶ агент
                                              │
агент: applyConfig() → зберігає локально, при disabled — чистить чергу
   │
   └─ POST /device/location/permissions {permission_state, background}
        └─ зміна стану ──▶ audit LOCATION_PERMISSION_CHANGED (актор = пристрій)
```

Якщо жодне поле не змінилося, команда не створюється й зайвого трафіку немає.

## 3. Збір на пристрої

Агент **не тримає постійну підписку** на оновлення позиції. Раз на тик
службового циклу він перевіряє, чи настав час, і робить один вимір через
`LocationManager` (AOSP, без залежності від Google Play Services):

- `getCurrentLocation()` на Android 11+, одноразовий `requestLocationUpdates`
  на старіших, `getLastKnownLocation` як запасний варіант (не старіше 10 хв);
- вибір провайдера: висока точність → `gps` → `fused` → `network`;
  економний режим → `network` → `fused` → `gps`;
- фіксується `isMock` — підроблена локація видно в панелі окремим бейджем.

### Батарея

Чиста, тестована логіка ([`BatteryPolicy`](../android/app/src/main/java/ua/fleet/agent/location/BatteryPolicy.kt)):

| Заряд (не на зарядці) | Поведінка |
|---|---|
| > 35 % | штатний інтервал, точність як налаштовано |
| ≤ 35 % | інтервал ×2 |
| ≤ 20 % | інтервал ×3, GPS вимикається |
| ≤ 10 % | збір призупиняється |
| на зарядці | завжди штатний режим |

### Фільтр зміщення

`min_distance_meters` відсікає «стояння на місці»: якщо пристрій змістився
менше ніж на задану відстань, координата не потрапляє в чергу (таймер при
цьому оновлюється). `0` вимикає фільтр.

## 4. Офлайн-черга та ретраї

[`LocationQueue`](../android/app/src/main/java/ua/fleet/agent/location/LocationQueue.kt) —
файл JSON Lines у приватному каталозі застосунку:

- місткість 2000 записів; при переповненні відкидаються **найстаріші**;
- відправка пакетами по 200 координат;
- записи видаляються з черги лише після підтвердження сервера;
- пошкоджений рядок не ламає читання решти.

Ретраї — експоненційна пауза від 1 хв, подвоєння за кожен збій, максимум
~1 година (`nextUploadAttemptAtMillis` у сховищі агента). Успішна відправка
скидає лічильник. Координати з черги позначаються `source=offline_queue`,
тож у таймлайні видно, що вони прийшли із затримкою.

## 5. Що зберігається на сервері

Таблиця `location_fixes`:

| Поле | Опис |
|---|---|
| `device_id` | пристрій (FK, каскадне видалення) |
| `latitude`, `longitude` | координати (валідація −90…90 / −180…180) |
| `accuracy_m` | радіус похибки в метрах |
| `altitude_m`, `speed_mps`, `bearing_deg` | якщо провайдер їх дав |
| `provider` | `gps` / `fused` / `network` — технічне джерело |
| `source` | `periodic` / `on_demand` / `offline_queue` — як потрапило на сервер |
| `is_mock` | ознака підробленої локації |
| `battery_level` | заряд на момент виміру |
| `recorded_at` | час виміру на пристрої |
| `received_at` | час приймання сервером (за ним працює ретеншн) |

Координати з `recorded_at` у майбутньому (>10 хв) або старіші за 7 днів
відхиляються — у відповіді видно `rejected`.

## 6. Політика зберігання

`LOCATION_HISTORY_DAYS` (за замовчуванням 90). Прибирання виконує фонова
задача [`retention_loop`](../backend/app/services/retention.py) кожні 6 годин
разом із телеметрією (`TELEMETRY_HISTORY_DAYS`) та аудитом
(`AUDIT_RETENTION_DAYS`). Результат запису — `RETENTION_RUN` в аудиті.

Позачерговий запуск: `POST /api/v1/maintenance/retention` (лише
`settings:manage`). Повне видалення історії пристрою — `DELETE
/devices/{id}/location/history`, теж з аудитом.

## 7. API

| Метод | Шлях | Дозвіл | Опис |
|---|---|---|---|
| GET | `/devices/{id}/location` | `location:read` | Зведення: конфіг, дозволи, остання позиція, лічильники |
| GET | `/devices/{id}/location/settings` | `location:read` | Лише конфігурація |
| PUT | `/devices/{id}/location/settings` | `location:manage` | Зміна (аудит + команда на пристрій) |
| POST | `/devices/{id}/location/request` | `location:manage` | Разовий вимір (409, якщо модуль вимкнено) |
| GET | `/devices/{id}/location/history` | `location:read` | Історія з фільтрами `since`/`until` (аудитується) |
| DELETE | `/devices/{id}/location/history` | `location:manage` | Видалення історії пристрою |

Агентські (device-JWT):

| Метод | Шлях | Опис |
|---|---|---|
| GET | `/device/location/config` | Поточна конфігурація |
| POST | `/device/location/permissions` | Стан дозволів → повертає конфігурацію |
| POST | `/device/location` | Пакет до 500 координат → `{accepted, rejected, config}` |

## 8. Панель

Вкладка **Геолокація** в картці пристрою:

- перемикач модуля, інтервал (1 хв … 6 год), фільтр зміщення, режим точності;
- стан звітування (активне / неактивне з причиною), стан дозволів
  (у т. ч. фонового), час останнього виміру, кількість записів і термін зберігання;
- карта Leaflet: маршрут, кола точності, найсвіжіша точка окремим кольором;
- таймлайн, синхронізований із картою; позначка `підроблена локація`;
- кнопки «запитати позицію зараз» і «видалити історію».

> **Приватність тайлів.** За замовчуванням карта тягне тайли з OpenStreetMap,
> тобто браузер оператора показує стороннньому сервісу приблизний район
> пристрою. Для повністю ізольованого розгортання задайте власний тайловий
> сервер: `VITE_MAP_TILE_URL` і `VITE_MAP_TILE_ATTRIBUTION`.

## 9. Аудит

| Дія | Коли |
|---|---|
| `LOCATION_CONFIG_CHANGED` | будь-яка зміна конфігурації (з `changes` «було → стало») |
| `LOCATION_DISABLED` | окрема подія на вимкнення модуля |
| `LOCATION_PERMISSION_CHANGED` | агент повідомив зміну стану дозволів (актор — пристрій) |
| `LOCATION_UPLOAD_REJECTED` | спроба надіслати координати при вимкненому модулі (`denied`) |
| `LOCATION_REQUESTED` | разовий запит позиції |
| `LOCATION_HISTORY_VIEWED` | перегляд історії переміщень оператором |
| `LOCATION_HISTORY_PURGED` | видалення історії |
| `RETENTION_RUN` | спрацював ретеншн (скільки рядків прибрано) |

---

## 10. Обмеження цієї версії

- Геозони (geofence) і сповіщення про вхід/вихід не реалізовані.
- Немає агрегації маршрутів (зупинки, пробіг) — лише сирі точки.
- Історія віддається сторінками до 5000 точок; кластеризація на карті ще
  не робиться, тому дуже довгі періоди краще фільтрувати через `since`.
- Точність позиціонування залежить від провайдера пристрою; агент не
  використовує Google Play Services, тому на деяких пристроях `network`-
  провайдер може бути менш точним, ніж fused у GMS.
