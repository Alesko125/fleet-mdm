# Реєстр команд

Версія: 1.0 · 2026-08-13

---

## 1. Головне правило

Віддаленої оболонки в системі **немає**. Не існує API, яке прийняло б рядок
і виконало його на пристрої: ані `/exec`, ані поля `command` чи `script` у
payload, ані шляху «протягнути» довільну дію через конфігурацію.

Виконати можна лише те, що описано в
[`app/services/command_registry.py`](../backend/app/services/command_registry.py).
Кожен запис реєстру каже:

| Поле | Навіщо |
|---|---|
| `type` | ідентифікатор; має бути і в `COMMAND_TYPE_VALUES` (CHECK у БД) |
| `title`, `description` | що це робить — людською мовою |
| `user_visible` | **що побачить власник пристрою**; порожнім не буває |
| `permission` | дозвіл за замовчуванням |
| `params_model` | схема параметрів (Pydantic, `extra="forbid"`) |
| `ttl_seconds` | скільки команда чекає на пристрій |
| `disruptive` | дія помітно втручається в роботу |
| `requires_device_owner` | спирається на `DevicePolicyManager` |
| `singleton_key` | чи можна мати дві такі команди одночасно |

Три рубежі не дають з'явитися команді поза реєстром:

1. `command_service.issue()` — єдиний вхід для видачі; невідомий тип →
   `404` і запис `COMMAND_REJECTED` в аудиті;
2. схема параметрів — зайве поле це помилка, а не мовчазне ігнорування;
3. `CHECK` у БД на колонку `commands.type`.

Тест `test_no_shell_like_command_exists` перевіряє, що в реєстрі немає ані
типу зі словом `SHELL`/`EXEC`/`RUN`/`SU`/`ADB`, ані схеми з полем
`command`/`script`/`args`.

## 2. Команди

| Тип | Дозвіл за замовчуванням | Механізм на пристрої | Помітна |
|---|---|---|---|
| `REBOOT` | `device:action:critical` | `DevicePolicyManager.reboot()` | так |
| `REFRESH_TELEMETRY` | `device:action:safe` | власні лічильники агента | ні |
| `SYNC_CONFIG` | `device:action:safe` | перечитування конфігурації з сервера | ні |
| `AGENT_RESTART` | `device:action:critical` | перезапуск власного foreground-сервісу | так |
| `COLLECT_DIAGNOSTICS` | `device:action:safe` | звіт про стан самого агента | ні |
| `APP_INSTALL` / `APP_UPDATE` | `app:manage` | `PackageInstaller` | залежить |
| `APP_UNINSTALL` | `app:manage` | `PackageInstaller` | так |
| `APP_LAUNCH` | `device:action:safe` | launch-intent | так |
| `APP_STOP` | `device:action:critical` | `killBackgroundProcesses` / `setPackagesSuspended` | так |
| `APP_LIST` | `device:action:safe` | інвентаризація пакетів | ні |

### Що означає «привілейована команда»

У цій системі привілейована = **потребує режиму Device Owner**, а не
«потребує root». Це принципово:

* `REBOOT` спирається на `DevicePolicyManager.reboot()` — задокументований
  API керування пристроєм. На пристрої без Device Owner команда не
  створюється взагалі: сервер відмовляє одразу з поясненням, а не лишає
  адміністратора з `failed` через п'ять хвилин;
* `APP_STOP` у режимі Device Owner використовує `setPackagesSuspended`,
  інакше — звичайний `ActivityManager.killBackgroundProcesses`;
* `su` у виконанні команд **не використовується взагалі**. Привілейований
  режим лишається тільки у файловому модулі — для каталогів, які
  адміністратор явно позначив `allow_privileged`, і там аргументи
  екрануються, а перелік утиліт фіксований (`ls`, `mkdir`, `mv`, `rm`).

### Чого команди не роблять

* не видаляють дані застосунків (`APP_STOP` лише завершує процеси);
* не читають системний `logcat` — діагностика збирає **власний** журнал
  агента з кільцевого буфера в памʼяті;
* не зупиняють самого агента (`APP_STOP` для пакета агента → `409`) —
  інакше пристрій став би некерованим, а власник утратив би видимий
  індикатор керування;
* не чіпають файли користувача — для файлів є окремий модуль зі своїм
  allowlist.

## 3. Життєвий цикл і поля запису

```
pending → dispatched → acked → succeeded | failed
                                └→ expired | cancelled
```

Кожен запис `commands` містить усе, що потрібно для розслідування:

| Поле | Опис |
|---|---|
| `id` | ідентифікатор команди |
| `device_id` | кому адресована |
| `created_by_id` | **хто видав** (адміністратор) |
| `created_at` | коли видана |
| `payload` | параметри після валідації |
| `status` | стан із переліку вище |
| `result` | що повернув пристрій |
| `error` | текст помилки, якщо не вдалося |
| `dispatched_at`, `acked_at`, `completed_at` | мітки етапів |
| `queue_ms` | скільки чекала, поки пристрій її забрав |
| `duration_ms` | **скільки виконувалася** на пристрої |

`queue_ms` і `duration_ms` рахуються з **серверних** міток
(`commands.measure`): годинник пристрою може розходитися з серверним, і
різниця «за даними пристрою» була б непорівнянною між пристроями.

## 4. Конфігуровані дозволи

Реєстр задає розумний дефолт. Змінити його можна без релізу — запис у
таблиці `command_permissions` перекриває значення для конкретного типу:

```http
PATCH /api/v1/commands/registry/REBOOT/permission
{"required_permission": "device:action:safe"}     # дозволити операторам

PATCH /api/v1/commands/registry/APP_UNINSTALL/permission
{"enabled": false}                                 # вимкнути зовсім

DELETE /api/v1/commands/registry/REBOOT/permission  # повернути дефолт
```

Змінювати матрицю може лише власник `settings:manage` (суперадміністратор),
і кожна зміна пише в аудит `COMMAND_PERMISSION_CHANGED` зі значеннями «до»
і «після».

**Чого конфігурація не може:** додати новий тип команди. Перекрити можна
лише потрібний дозвіл і прапорець «увімкнено» для типу, який уже є в
реєстрі — інакше налаштування стало б способом протягнути довільну дію повз
перевірки. Спроба налаштувати неіснуючий тип → `404`.

Вимкнену команду не видасть навіть суперадміністратор.

Право **скасувати** команду дорівнює праву її **видати**: хто міг створити
команду цього типу, той може її і зняти.

## 5. API

| Метод | Шлях | Дозвіл | Опис |
|---|---|---|---|
| GET | `/commands/registry` | `device:read` | Усі типи: параметри, хто має право, що побачить користувач |
| PATCH | `/commands/registry/{type}/permission` | `settings:manage` | Змінити правило |
| DELETE | `/commands/registry/{type}/permission` | `settings:manage` | Повернути дефолт |
| POST | `/devices/{id}/commands` | перевіряє реєстр | **Видати команду** |
| GET | `/commands`, `/devices/{id}/commands` | `device:read` | Історія з фільтрами |
| GET | `/commands/{id}` | `device:read` | Деталі + довідка про тип |
| GET | `/commands/stats` | `device:read` | Зведення за типами й тривалості |
| POST | `/commands/{id}/cancel` | як у видачі | Скасувати незавершену |

```http
POST /api/v1/devices/{id}/commands
{"type": "COLLECT_DIAGNOSTICS", "params": {"log_lines": 100}}

202 Accepted
{"id": "…", "type": "COLLECT_DIAGNOSTICS", "status": "pending", …}
```

Для зручності панелі є й спеціалізовані ендпоїнти
(`POST /devices/{id}/reboot`, `/telemetry/refresh`, `/config/sync`,
`/agent/restart`, `/diagnostics`, `/apps/stop`). Вони роблять те саме
через `command_service.issue`, тож перенастроєна матриця дозволів діє і
там — це перевірено тестом.

## 6. Аудит

Кожна видача пише **дві** події:

* `COMMAND_ISSUED` — однорідний слід для всіх команд: тип, пристрій,
  параметри, чи помітна дія, чи потребує Device Owner;
* доменна подія типу (`DEVICE_REBOOT`, `APP_INSTALL`, `AGENT_RESTART`,
  `DIAGNOSTICS_COLLECTED`…) — щоб звичні фільтри журналу далі працювали.

Відмови теж фіксуються — `COMMAND_REJECTED` з причиною:

| `reason` | Коли |
|---|---|
| `unknown_command` | типу немає в реєстрі |
| `command_disabled` | команду вимкнено адміністратором |
| `permission_denied` | ролі бракує чинного дозволу |
| `device_owner_required` | пристрій не в режимі Device Owner |
| `device_not_active` | пристрій призупинено або знято з обліку |

Завершення пише `COMMAND_COMPLETED` із результатом і тривалістю,
скасування — `COMMAND_CANCELLED`.

## 7. Панель

* **Реєстр команд** (окрема сторінка) — усі типи, їхні параметри, хто має
  право, що побачить користувач пристрою, статистика виконання; тут же
  редагується матриця дозволів.
* **Картка пристрою → Огляд** — кнопки дій, побудовані **з реєстру**:
  недоступні дії вимкнені з поясненням («потрібен дозвіл …», «потрібен
  режим Device Owner», «команду вимкнено»). Помітні дії просять
  підтвердження й показують, що саме побачить власник пристрою.
* **Історія операцій** — фільтри за типом (теж із реєстру) і станом,
  час у черзі та час виконання.

## 8. Обмеження цієї версії

- `POLICY_APPLY` і `KIOSK_SET` є в переліку типів БД, але ще не мають
  запису в реєстрі — тобто видати їх поки не можна.
- Пакетна видача (одна команда на групу пристроїв) не реалізована: зараз
  це окремий виклик на пристрій.
- Планувальника («виконати о 03:00») немає.
- Діагностика повертається як JSON у `result`; вивантаження великого
  архіву логів пішло б через файловий модуль, але автоматично це не
  робиться.
