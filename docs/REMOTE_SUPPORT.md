# Модуль віддаленої підтримки

Версія: 1.0 · 2026-08-12 · відповідає Milestone 7

Оператор може побачити екран пристрою — **тільки після того, як людина за
цим пристроєм явно погодиться**, і тільки поки вона цього не скасувала.

---

## 1. Три бар'єри перед показом екрана

| # | Бар'єр | Де |
|---|---|---|
| 1 | Сервер не переводить сеанс у `active`, доки агент не надішле згоду | [`support.py:mark_started`](../backend/app/services/support.py) — без `consent_at` кидає `PermissionDeniedError` |
| 2 | Агент показує власний екран запиту: хто саме просить (пошта адміністратора) і чому | [`SupportConsentActivity`](../android/app/src/main/java/ua/fleet/agent/support/SupportConsentActivity.kt) |
| 3 | Android показує **системний** діалог `MediaProjection` і тримає індикатор трансляції | штатний API, ми його не обходимо |

Додатково під час сеансу працює foreground-сервіс із **постійним сповіщенням**
і кнопкою «Зупинити»: користувач обриває показ будь-якої миті, не питаючи
нікого. Прихованого захоплення екрана в системі немає — і не може бути:
`MediaProjection` без згоди просто не видає `VirtualDisplay`.

Тест `test_stream_without_consent_is_impossible` фіксує це на рівні коду.

## 2. Життєвий цикл

```
адмін → POST /devices/{id}/support-sessions {reason, input_enabled, max_duration_minutes}
          │  state = requested,  join_secret (показується один раз)
          │  audit REMOTE_SESSION_REQUESTED
          ▼
      команда REMOTE_SUPPORT_REQUEST ──► агент ──► екран згоди
          │
          ├─ «Відхилити» → POST /device/support-sessions/{id}/consent {granted:false}
          │        state = denied, audit REMOTE_SESSION_CONSENT (result=denied)
          │
          └─ «Дозволити» → системний діалог MediaProjection
                   └─ POST .../consent {granted:true, input_available}
                          state = awaiting_consent, consent_at, audit
          ▼
   WS /ws/support/{id}?role=device  → mark_started → state = active
          │                             audit REMOTE_SESSION_STARTED
          │  кадри (бінарні фрейми) ──► WS /ws/support/{id}?role=viewer
          ▼
   завершення: адміністратор, користувач пристрою, таймаут або втрата потоку
          state = ended | expired, audit REMOTE_SESSION_ENDED
```

Одночасно на пристрій дозволено **лише один** відкритий сеанс.

### Таймаути

| Ситуація | Поріг | Результат |
|---|---|---|
| Користувач не відповів на запит | 180 с | `expired`, `consent_timeout` |
| Досягнуто максимальної тривалості | `max_duration_minutes` (типово 30 хв) | `expired`, `max_duration_reached` |
| Кадри перестали надходити | 90 с | `ended`, `stream_lost` |

Прострочені сеанси закриває фонова задача (той самий цикл, що й моніторинг),
тож «забутий» сеанс не може висіти відкритим необмежено довго.

## 3. Транспорт і секрети

* Канал — `WSS` (TLS-термінація в nginx, `proxy_read_timeout 3600s`).
* Кадри йдуть **бінарними** WebSocket-фреймами (JPEG), керуючі повідомлення — JSON.
* Приєднатися до перегляду можна двома шляхами, і обидва прив'язані до
  конкретного сеансу:
  * **квиток перегляду** (штатний для панелі) — `POST /support-sessions/{id}/viewer-ticket`
    видає одноразовий токен із TTL 60 с, прив'язаний до пари «сеанс + оператор».
    Погашення робиться `GETDEL`, тож перехоплений квиток не спрацює вдруге,
    навіть якщо два підключення прийдуть одночасно;
  * **`join_secret`** (32 байти CSPRNG) — віддається один раз під час створення
    сеансу, у БД лежить лише `HMAC-SHA256`. Лишається для сценаріїв без браузера.

  Квиток з'явився не для зручності: раніше єдиним ключем був довгоживучий
  секрет, який доводилося тримати в пам'яті вкладки весь сеанс. Перезавантаження
  сторінки означало втрату перегляду, а перепідключення після обриву мережі —
  теж. Тепер панель бере свіжий квиток на кожне підключення й не зберігає
  нічого чутливого.
* Одного лише валідного access-токена для приєднання недостатньо: потрібен
  ще й дозвіл `support:session`, і квиток (або секрет) саме цього сеансу.
* Пристрій автентифікується device-JWT і може підключитися лише до **свого**
  сеансу; чужий `session_id` дає `4401`.
* Ретрансляція кадрів відбувається в межах одного процесу API. Для кількох
  реплік достатньо липкої маршрутизації `/ws/support/` у nginx — гнати
  відеопотік через Redis pub/sub дорого й непотрібно.

## 4. Адаптація до каналу

Сервер раз на 5 секунд рахує фактичний бітрейт сеансу і надсилає пристрою
підказку:

| Бітрейт | к/с | Масштаб | JPEG |
|---|---|---|---|
| < 300 кбіт/с | 2 | 35 % | 45 |
| < 1 Мбіт/с | 4 | 50 % | 55 |
| < 3 Мбіт/с | 8 | 70 % | 70 |
| ≥ 3 Мбіт/с | 12 | 100 % | 80 |

Агент застосовує підказку на льоту: змінює частоту захоплення, масштаб
зменшення та якість стиснення. Оператор може надіслати власну підказку
повідомленням `{"type":"quality", ...}`.

### Перепідключення

Розрив каналу не завершує сеанс миттєво — перепідключаються **обидві** сторони.

**Агент:** пауза 2 → 4 → … → 30 с, згода зберігається. Після кожного
відкриття каналу він наново надсилає роздільність екрана: сервер міг втратити
попереднє значення, а без нього керування недоступне. Сеанс закриється лише
якщо кадрів немає довше за 90 секунд, або якщо сервер закрив канал кодом
`4403/4409` (згоду відкликано / сеанс завершено) — тоді агент більше не
намагається.

**Панель:** та сама схема з паузою 2 → 4 → … → 20 с, щоразу зі свіжим
квитком перегляду. Коди `4403/4409` теж означають «більше не пробувати».
Стан підключення показується окремим індикатором: `підключаємось`,
`канал підключено`, `перепідключення…`, `канал закрито`.

### Стан підключення

Хто зараз у каналі — рахує сервер, а не клієнт. Присутність живе в Redis
(`support:{id}:device_online`, `support:{id}:viewers`, TTL 20 с):
пристрій оновлює її під час надсилання кадрів, оператор — пінгом раз на 5 с.

`GET /support-sessions/{id}/connection` повертає:

```json
{"device_online": true, "viewers": 1, "streaming": true,
 "seconds_since_frame": 2, "frame_width": 1080, "frame_height": 2400}
```

Раніше панель здогадувалася про це з того, чи прилітають кадри в її власний
сокет. Тепер картина однакова для всіх операторів і не залежить від того,
до якої репліки API вони підключені.

## 5. Віддалене керування

Керування можливе **лише** якщо збіглися три умови:

1. адміністратор запросив його під час створення сеансу (`input_enabled`);
2. на пристрої увімкнена служба доступності Fleet Агента — вмикає її
   виключно користувач у системних налаштуваннях;
3. агент підтвердив це в згоді (`input_available: true`).

Якщо пристрій відповів `input_available: false`, сервер **знижує** прапорець
сеансу до `false` — і повторна відповідь уже нічого не змінить
(`test_repeated_consent_cannot_escalate_access`).

Четверта умова — технічна: сервер має знати **роздільність екрана пристрою**.
Кадри масштабуються під канал (35–100 %), тож із розміру картинки в браузері
координати вивести не можна: дотик потрапив би не туди. Агент надсилає
`{"type":"metrics","width":…,"height":…,"density_dpi":…}` при кожному
відкритті каналу; поки цього повідомлення не було, панель показує
«керування недоступне», а сервер відхиляє дії з `input_unavailable`.

Панель перераховує клік у координати пристрою за часткою від розміру
елемента `<img>`, а не за пікселями картинки.

### Що сервер погоджується ретранслювати

Сервер — не прозора труба до пристрою. Кожне повідомлення `input`
перевіряється (`support_service.sanitize_input`):

* дія має бути з переліку `tap`, `swipe`, `back`, `home`, `recents`;
* координати — цілі числа в межах відомої роздільності;
* тривалість свайпу затискається в 50–3000 мс;
* усі зайві поля відкидаються — на пристрій іде заново зібраний об'єкт.

Права перевіряються **на кожну дію**, а не лише при підключенні: стан сеансу
й дозволи оператора перечитуються з БД (кеш 2 с). Якщо адміністратор вимкнув
керування або користувач завершив сеанс — наступний дотик уже не пройде,
а сокет закриється.

Реалізація на пристрої — штатний `AccessibilityService.dispatchGesture()`:
тап, свайп, «назад», «додому», «останні». Служба налаштована з
`canRetrieveWindowContent="false"` — вміст екрана через неї не читається.
Жодних обхідних шляхів (інʼєкція подій через `su`, `input tap`) немає:
керування чужим екраном має лишатися явно дозволеним і видимим.

## 6. API

| Метод | Шлях | Дозвіл |
|---|---|---|
| POST | `/devices/{id}/support-sessions` | `support:session` |
| GET | `/support-sessions` | `device:read` (фільтри `device_id`, `state`) |
| GET | `/support-sessions/{id}` | `device:read` |
| POST | `/support-sessions/{id}/stop` | `support:session` |
| POST | `/support-sessions/{id}/viewer-ticket` | `support:session` — одноразовий квиток на приєднання |
| GET | `/support-sessions/{id}/connection` | `device:read` — живий стан каналу |
| GET | `/support-sessions/{id}/audit` | `audit:read` — журнал подій сеансу |
| POST | `/devices/{id}/support-sessions/refresh` | `support:session` — повторно надіслати запит |

Агентські (device-JWT): `GET /device/support-sessions/{id}`,
`POST /device/support-sessions/{id}/consent`,
`POST /device/support-sessions/{id}/end`.

WebSocket:

* пристрій — `/ws/support/{id}?role=device&token=<device-JWT>`;
* оператор — `/ws/support/{id}?role=viewer&token=<access-JWT>&ticket=<квиток>`
  (або `&secret=<join_secret>` для не-браузерних клієнтів).

Повідомлення каналу оператора:

| Напрям | Тип | Призначення |
|---|---|---|
| ← сервер | `joined` | стан при підключенні: чи транслює, чи готове керування, роздільність |
| ← сервер | `metrics` | нова роздільність кадру (агент перепідключився) |
| ← сервер | `stream_ended` | пристрій вийшов із каналу |
| ← сервер | `error` | `input_disabled`, `input_unavailable`, `bad_input`, `frame_too_large` |
| → сервер | `ping` | підтвердження присутності (раз на 5 с) |
| → сервер | `input` | дія керування |
| → сервер | `quality` | ручна підказка якості |

## 7. Панель

Вкладка **Підтримка** в картці пристрою:

* **форма запиту**: причина (обовʼязкова, її бачить користувач), максимальна
  тривалість, прапорець «запросити керування»;
* **активний сеанс**: стан сеансу, стан каналу, чи пристрій у мережі,
  кількість глядачів, лічильник тривалості, кадри й трафік, секунди від
  останнього кадру, роздільність, кількість перепідключень, кнопка
  «Завершити», живий екран (бінарні кадри малюються в `<img>`);
* **керування** (якщо доступне): клік по зображенню = дотик, кнопки «Назад»,
  «Головний екран», «Останні застосунки». Кнопки неактивні, доки пристрій не
  підтвердив підтримку й не надіслав роздільність;
* **історія сеансів**: стан, адміністратор, причина, тривалість, трафік,
  кількість дій керування, час — і розкривний **журнал аудиту** кожного
  сеансу окремо.

Нічого чутливого панель не зберігає: квиток перегляду береться заново на
кожне підключення й живе 60 секунд, тож ані `localStorage`, ані пам'ять
вкладки не тримають довгоживучого ключа до каналу.

### Що бачить користувач пристрою

Стан підтримки видимий у чотирьох місцях одночасно, і жодне з них агент
не приховує:

1. екран згоди з іменем адміністратора та причиною — до початку трансляції;
2. постійне сповіщення foreground-сервісу з кнопкою «Зупинити»;
3. системний індикатор трансляції Android (`MediaProjection`);
4. картка «Віддалена підтримка» на головному екрані агента: стан каналу,
   хто дивиться, причина, тривалість, кількість перепідключень, чи
   ввімкнене керування — і своя кнопка зупинки.

## 8. Аудит

| Дія | Коли |
|---|---|
| `REMOTE_SESSION_REQUESTED` | адміністратор створив запит (хто, причина, тривалість, чи просив керування) |
| `REMOTE_SESSION_CONSENT` | відповідь користувача: `success` — згода, `denied` — відмова |
| `REMOTE_SESSION_STARTED` | пристрій під'єднався і почав трансляцію |
| `REMOTE_SESSION_ENDED` | завершення: ким, чому, скільки тривало, скільки кадрів, байтів і дій керування |
| `REMOTE_SESSION_VIEWER_JOINED` | оператор отримав квиток (`denied` — спроба з чужим/простроченим) |
| `REMOTE_SESSION_VIEWER_LEFT` | оператор відʼєднався; скільки дій керування зробив |
| `REMOTE_SESSION_INPUT` | підсумок дій керування: скільки й яких типів |

Актор фіксується точно: адміністратор (`user`), пристрій (`device`) або
`system` для автоматичних закриттів. Для дій оператора зберігається IP.

Дії керування пишуться **пачкою**, а не по одній: окремий запис на кожен тап
зробив би журнал нечитабельним, тому фіксується підсумок при відʼєднанні
оператора — скільки дій і яких саме типів.

Увесь журнал конкретного сеансу доступний одним запитом
`GET /support-sessions/{id}/audit` і показується в панелі під рядком історії.

## 9. Обмеження цієї версії

- Транспорт — WebSocket + JPEG-кадри. WebRTC (H.264, менша затримка) у схемі
  передбачений полем `transport`, але не реалізований.
- Звук не передається взагалі.
- Кадри не зберігаються на сервері: запису сеансу немає (це свідомо — менше
  чутливих даних у спокої).
- Перегляд одночасно кількома операторами працює; панель показує їхню
  кількість, але не імена — окремого переліку «хто саме дивиться» ще немає.
- Керування — тап, свайп і три глобальні дії. Введення тексту й апаратні
  клавіші (гучність, живлення) через `AccessibilityService` не реалізовані.
- Для кількох реплік API потрібна липка маршрутизація `/ws/support/`.
