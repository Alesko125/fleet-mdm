# Архітектура Fleet MDM

> Self-hosted платформа керування Android-пристроями, які **явно зареєстровані
> їхнім власником**. Уся телеметрія й керування відбуваються через задокументовані
> Android API (Device Owner / Device Policy Manager / PackageManager /
> MediaProjection). Агент завжди видимий користувачу пристрою.

Версія документа: 1.0 · 2026-08-12

---

## 1. Межі системи та принципи

### Що система робить

| Модуль | Призначення |
|---|---|
| Enrollment | Реєстрація пристрою за одноразовим токеном, видача криптоідентичності |
| Inventory | Інвентаризація заліза/ОС/мережі, телеметрія, статус онлайн |
| Applications | Список застосунків, встановлення/оновлення/видалення/запуск APK |
| Administration | Reboot, оновлення телеметрії, синхронізація конфігурації, kiosk-політики |
| Files | Доступ **лише** до явно налаштованих каталогів (allowlist) |
| Location | Opt-in геолокація з видимим статусом і журналом змін налаштувань |
| Remote support | Сеанс віддаленої підтримки з явною згодою та індикацією на екрані |
| Security | TLS, JWT+refresh, RBAC, per-device ключі, ротація, rate limit, аудит |
| Audit | Незмінний журнал усіх адміністративних дій |
| Dashboard | Веб-панель оператора |

### Чого система свідомо НЕ робить

Це архітектурне обмеження, а не «поки не реалізовано»:

- ❌ кейлогінг, перехоплення введення, читання буфера обміну у фоні;
- ❌ приховане аудіо/відео записування, доступ до мікрофона/камери без індикації;
- ❌ перехоплення SMS/дзвінків/повідомлень сторонніх месенджерів;
- ❌ викрадення облікових даних, читання чужих токенів/паролів;
- ❌ будь-які механізми приховування агента (іконка, сповіщення, запис у
  «Налаштування → Керування пристроєм» лишаються видимими);
- ❌ обхід дозволів Android, root-експлойти, приховане підвищення привілеїв.

Екран віддаленої підтримки використовує `MediaProjection`, який **завжди**
показує системний діалог згоди й постійний індикатор трансляції. Ми не
намагаємось його обійти.

### Правова рамка

Платформа розрахована на пристрої, що належать організації або особі, яка
самостійно їх реєструє. Перед розгортанням переконайтеся, що користувачів
поінформовано письмово (в Україні — ЗУ «Про захист персональних даних»,
ст. 163 ККУ щодо таємниці листування; в ЄС — GDPR ст. 6/13 та ePrivacy).

### Потоки даних

```
Реєстрація      агент ──FLEET-токен + публічний ключ──▶ сервер ──device_id──▶ агент
Автентифікація  агент ◀──nonce── сервер ; агент ──підпис P-256──▶ сервер ──device-JWT──▶
Команда         оператор ──реєстр+RBAC──▶ сервер ──Redis pub/sub──▶ WS ──▶ агент
                агент ──ack → progress → result──▶ сервер ──queue_ms / duration_ms──▶ аудит
Підтримка       оператор ──квиток (60 с)──▶ WSS ; агент ──JPEG-кадри──▶ оператор
                                            (лише після згоди користувача)
Чутливі дані    агент ──TLS──▶ сервер ──AES-256-GCM──▶ PostgreSQL
                                            (ключ в оточенні, не в БД)
```

### Компоненти

| Сервіс | Технологія | Роль |
|---|---|---|
| `nginx` | nginx:alpine | TLS-термінація, HSTS, проксі WS, ліміт розміру тіла |
| `api` | FastAPI + uvicorn | REST + WebSocket, бізнес-логіка, аудит |
| `postgres` | PostgreSQL 16 | Джерело істини: пристрої, команди, аудит, історія |

## 3. Ідентичність і довіра

Система має **два незалежні класи суб'єктів** і два різні механізми автентифікації.

### 3.1 Оператори (люди)

```
POST /api/v1/auth/login      email + пароль (Argon2id)
   → access JWT  (15 хв, у пам'яті SPA)
   → refresh JWT (14 днів, httpOnly cookie або secure storage)

POST /api/v1/auth/refresh    ротація: старий refresh анулюється,
                             видається новий у тій самій «родині» (family)
                             повторне використання анульованого →
                             вся родина відкликається + AUTH_REFRESH_REUSE в аудиті
```

### 3.2 Пристрої (агенти) — challenge–response, без спільного секрету

Ключ пристрою **ніколи не залишає Android Keystore** (де є StrongBox — апаратний):

```
1. Адмін:   POST /api/v1/enrollment/tokens      → одноразовий токен (показується один раз)
2. Агент:   генерує EC P-256 у Keystore (setUserAuthenticationRequired=false,
            setAttestationChallenge для перевірки апаратного походження)
3. Агент:   POST /api/v1/enroll  { token, public_key(SPKI/DER→base64), device_info }
            ← { device_id, server_time, policy_snapshot }
4. Агент:   POST /api/v1/device/auth/challenge { device_id }   ← { nonce, expires_at }
5. Агент:   підписує nonce ключем з Keystore (SHA256withECDSA)
            POST /api/v1/device/auth/token { device_id, nonce, signature }
            ← device access JWT (1 год, scope=device:<id>)
6. Агент:   WSS /ws/device з Bearer device-JWT
```

Компрометація БД сервера не дає можливості видати себе за пристрій — там лише
публічні ключі. Enrollment-токени зберігаються як HMAC-SHA256, не у відкритому вигляді.

## 4. Транспорт: REST + WebSocket

### REST (`/api/v1`)

Синхронні операції: CRUD, конфігурація, вивантаження телеметрії, завантаження
файлів/APK, читання аудиту. Усі відповіді — JSON, помилки у форматі
`{"error": {"code": "...", "message": "...", "details": {...}}}`.

### WebSocket

| Endpoint | Суб'єкт | Призначення |
|---|---|---|
| `/ws/device` | агент | Командний канал: сервер → пристрій, ACK/результат назад |
| `/ws/admin` | оператор | Живі оновлення: онлайн-статус, прогрес команд, нова телеметрія |
| `/ws/support/{session_id}` | обидва | Кадри екрана та керуючі повідомлення сеансу підтримки |

Між репліками API повідомлення розходяться через **Redis pub/sub**
(канали `device:{id}`, `admin:events`, `support:{session_id}`), тому
горизонтальне масштабування не потребує «липких» сесій.

### Життєвий цикл команди

```
адмін → POST /devices/{id}/commands
          │
          ▼
    commands(status=pending) ──publish──▶ Redis ──▶ WS-з'єднання агента
          │                                              │
          │                                              ▼ виконання
          │◀──────── ACK (dispatched → acked) ───────────┤
          │◀──────── результат (succeeded/failed) ───────┘
          ▼
   audit_log + WS /ws/admin
```

Якщо пристрій офлайн — команда лишається `pending` і доставляється при
підключенні; після `expires_at` переходить у `expired`. Кожна команда має
`idempotency_key`, тож повтор доставки не виконує дію двічі.

## 6. Безпека (зведення)

Деталі — [SECURITY.md](SECURITY.md).

- **TLS-ready**: nginx з сучасним ciphers-набором, HSTS, готовність до Let's Encrypt;
  API також вміє працювати за проксі (`X-Forwarded-*` враховуються лише від довіреного проксі).
- **Паролі**: Argon2id; блокування після N невдалих спроб.
- **JWT**: короткий access, refresh із ротацією та виявленням повторного використання.
- **RBAC**: `superadmin` › `admin` › `operator` › `auditor`, перевірка на рівні залежності FastAPI.
- **Rate limiting**: Redis, окремі ліміти на login / enroll / загальний API.
- **Валідація**: Pydantic v2 на вході; шляхи файлів нормалізуються й перевіряються
  проти allowlist (захист від `..`-traversal).
- **Секрети**: лише через env/Docker secrets; сервер відмовляється стартувати
  в production з дефолтними ключами.
- **Аудит**: кожна адміністративна дія пишеться синхронно в тій самій транзакції.
