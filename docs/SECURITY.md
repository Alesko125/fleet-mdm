# Модель безпеки Fleet MDM

Версія: 2.0 · 2026-08-13 · підсумки аудиту — [SECURITY_AUDIT.md](SECURITY_AUDIT.md)

---

## 1. Принципи

1. **Прозорість перед власником пристрою.** Агент видимий: іконка в лаунчері,
   постійне сповіщення foreground-сервісу, екран статусу зі списком того, що
   збирається і хто адміністратор. Приховування агента не реалізується.
2. **Мінімум привілеїв.** Кожна можливість вмикається окремо (геолокація —
   opt-in, файли — лише allowlist каталогів, підтримка — лише за згодою).
3. **Немає спільних секретів між пристроями.** У кожного власна пара ключів.
4. **Все адміністративне — в аудиті.** Незмінний журнал, запис у тій самій
   транзакції, що й сама дія.

## 2. Автентифікація

### 2.1 Оператори

| Контроль | Реалізація |
|---|---|
| Хешування паролів | Argon2id (`argon2-cffi`), параметри за замовчуванням бібліотеки |
| Політика пароля | мінімум 12 символів, перевірка на вході (Pydantic) |
| Брутфорс | лічильник `failed_login_count` + `locked_until` у БД **та** rate limit у Redis |
| Access token | JWT HS256, TTL 15 хв, `typ=access`, `jti`, `iat_ms`, `iss`, `aud`; зберігається лише в памʼяті вкладки |
| Refresh token | JWT + запис у БД з `token_hash` (HMAC-SHA256), TTL 14 днів; віддається **виключно** cookie `HttpOnly; Secure; SameSite=strict` |
| Ротація refresh | при кожному `/auth/refresh` старий → `revoked`, видається новий у тій самій `family_id` |
| Виявлення крадіжки | повторне використання анульованого refresh → відкликається **вся родина**, подія `AUTH_REFRESH_REUSE` в аудиті |
| Миттєве відкликання | `users.sessions_valid_from`: токени, видані раніше цієї мітки, не приймаються ніде — ні в REST, ні у WebSocket |
| Вихід | `/auth/logout` анулює поточну родину; `/auth/logout-all` — усі сесії користувача |
| CSRF | double-submit: cookie `fleet_csrf` + заголовок `X-CSRF-Token`; перевіряється на кожному небезпечному методі, де є cookie сесії |

### Чому саме так

**Refresh-токен недоступний скриптам.** Він живе тільки в HttpOnly-cookie з
`Path=/api/v1/auth`, тож знайдений XSS не може ані прочитати його, ані
вивезти назовні. У `localStorage` панелі лишається лише прапорець «сесія
була», щоб після перезавантаження сторінки одразу спробувати оновлення.

**Access-токен відкликається негайно.** `jti` навмисно не зберігається в БД
(це коштувало б запиту на кожен виклик), але мітка `sessions_valid_from`
дає той самий результат однією перевіркою вже завантаженого рядка
користувача. Мітка зсувається при: виході, `logout-all`, зміні пароля,
зміні ролі, деактивації, скиданні пароля адміністратором.

Токен несе `iat_ms` (мілісекунди) — посекундного `iat` не вистачало, щоб
відрізнити токен, виданий *до* відкликання, від виданого одразу *після*
нього в ту саму секунду.

### 2.2 Пристрої

- Ключ EC P-256 генерується **у Android Keystore** (`setIsStrongBoxBacked(true)`
  за наявності апаратної підтримки), приватна частина невивантажувана.
- Enrollment передає лише публічний ключ (SPKI/DER, base64).
- Автентифікація — challenge–response: сервер видає одноразовий `nonce`
  (Redis, TTL 120 с, видаляється при використанні), агент підписує
  `SHA256withECDSA`, сервер перевіряє публічним ключем.
- У разі успіху видається device-JWT (`typ=device`, TTL 1 год, `sub=device_id`).
- `nonce` одноразовий → захист від replay. Підпис прив'язаний до `device_id`.
- Токен несе `scope=device:<id>`, який звіряється з `sub`.
- `devices.tokens_valid_from` відкликає видані токени негайно — при
  призупиненні, видаленні пристрою та ротації ключа.

### 2.4 Ротація облікових даних пристрою

Ключ пристрою не вічний: `DEVICE_KEY_MAX_AGE_DAYS` (типово 180) задає вік,
після якого сервер позначає ключ як такий, що підлягає перевипуску, і
повідомляє про це агента у відповіді на автентифікацію.

Перевипуск ініціює **агент**, бо тільки він має приватну частину:

1. `POST /device/key/challenge` — одноразовий `nonce` в окремому просторі
   імен (nonce автентифікації для ротації не годиться і навпаки);
2. агент створює нову пару в Keystore під псевдонімом наступного покоління
   (`fleet_device_identity_v<n>`), стара при цьому лишається робочою — обрив
   мережі нічого не ламає;
3. агент підписує `fleet-device-key-rotation:<device_id>:<sha256(новий
   ключ)>:<nonce>` **старим** ключем: володіння чинним ключем — єдиний
   доказ, що ротацію просить саме цей пристрій, а не власник вкраденого
   токена;
4. `POST /device/key/rotate` перевіряє підпис, переносить старий публічний
   ключ у `device_key_history`, підвищує `key_generation` і зсуває
   `tokens_valid_from` — усі видані токени вмирають;
5. лише після відповіді сервера агент робить нову пару поточною й видаляє
   стару. Відмова сервера — заготовка прибирається, працює старий ключ.

Обмеження: `DEVICE_KEY_ROTATION_DAILY_LIMIT` ротацій на добу; відкликаний
ключ не можна ані повернути, ані зареєструвати з ним новий пристрій
(перевірка за `device_key_history`); нова крива — тільки P-256.

Адміністратор із дозволом `device:credential:rotate` може вимагати
перевипуску (`POST /devices/{id}/credentials/rotate`) або одразу для всіх
прострочених (`POST /maintenance/device-keys/rotate-overdue`). Сам ключ із
панелі підмінити **неможливо** — приватна частина ніколи не залишає
Android Keystore.

### 2.3 Enrollment-токени

- 32 байти CSPRNG → base32 без неоднозначних символів, формат `FLEET-XXXX-XXXX-XXXX-XXXX`.
- У БД зберігається лише `HMAC-SHA256(TOKEN_HASH_SECRET, token)` + короткий префікс для UI.
- Обмеження: TTL (за замовчуванням 24 год), `max_uses`, ручне відкликання.
- Показується адміністратору **один раз** одразу після створення.
- Спроби enrollment обмежені rate-limit'ом за IP (`RATE_LIMIT_ENROLL`).

## 3. Авторизація (RBAC)

| Роль | Права |
|---|---|
| `superadmin` | усе, включно з керуванням користувачами й глобальними налаштуваннями |
| `admin` | пристрої, застосунки, файли, політики, геолокація, сеанси підтримки |
| `operator` | перегляд + безпечні дії (refresh telemetry, sync config, запуск застосунку, сеанс підтримки) |
| `auditor` | лише читання, включно з аудит-журналом; не бачить вмісту файлів |

Ролі строго вкладені: кожна наступна лише додає права
(`auditor ⊂ operator ⊂ admin ⊂ superadmin`) — це перевіряється тестом.

Окремо винесені два чутливі дозволи:

| Дозвіл | Роль | Що дає |
|---|---|---|
| `device:credential:rotate` | `admin`+ | вимагати перевипуску ключа пристрою, відкликати його токени |
| `secret:rotate` | `superadmin` | бачити стан ротації серверних секретів |

Перевірка виконується залежністю `require_role(...)` / `require_permission(...)`
до виконання будь-якої бізнес-логіки. Відмова пишеться в аудит з `result=denied`.

Матриця дозволів визначена в одному місці — `app/core/rbac.py`; вона ж
віддається клієнту в `/auth/me`, щоб панель ховала недоступні дії. Роль
береться **з БД**, а не з claims токена: зміна ролі діє негайно.

WebSocket-канали проходять ту саму перевірку: `/ws/admin` вимагає
`device:read`, канал підтримки — `support:session`, а стан сеансу й права
оператора перечитуються під час роботи, а не лише при підключенні.

## 4. Транспорт і розгортання

- nginx термінує TLS 1.2/1.3, лише AEAD-шифри з forward secrecy, HSTS
  (`max-age=31536000; includeSubDomains; preload`), OCSP stapling,
  вимкнені session tickets.
- HTTP → 301 на HTTPS; ACME-челендж проксується на `/.well-known/acme-challenge/`.
- Заголовки безпеки: `Content-Security-Policy` (без `unsafe-inline` для
  скриптів), `X-Content-Type-Options`, `X-Frame-Options: DENY`,
  `Referrer-Policy`, `Cross-Origin-Opener-Policy`,
  `Cross-Origin-Resource-Policy`, `Permissions-Policy`. Ставляться і
  застосунком (`app/core/middleware.py`), і nginx — щоб панель не лишилася
  без політики через чужу конфігурацію проксі.
- Відповіді API — `Cache-Control: no-store`.
- Обмеження тіла: 1 МБ за замовчуванням, `MAX_UPLOAD_MB` — точково на
  маршрутах вивантаження; застосунок перевіряє це самостійно
  (`RequestGuardMiddleware`), не покладаючись лише на проксі.
- У журнал nginx пишеться `$uri`, а не `$request_uri`: браузерний WebSocket
  передає токен параметром URL, і повний рядок запиту осідав би в логах.
- API довіряє `X-Forwarded-For` лише від адрес довіреного проксі (`TRUSTED_PROXIES`)
  і приймає лише `Host` зі списку `ALLOWED_HOSTS`.
- Postgres і Redis **не публікують портів** назовні; у режимі розробки —
  лише на `127.0.0.1`.
- Контейнери: `no-new-privileges`, `cap_drop: [ALL]`, `read_only` для API.
- Android-агент використовує TLS з перевіркою ланцюга; у релізній збірці
  `http://` відхиляється взагалі. Для self-signed деплою передбачено network
  security config із власним CA (без `trustAll`).
- Агент надсилає свій токен лише на хост, отриманий під час enrollment
  (`ServerUrlGuard`): посилання з payload команди не можуть вивести токен
  на сторонній сервер.

### Конфігурація розгортання

`docker compose up` піднімає **production**-конфігурацію. Оточення розробки
підключається лише явно:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d   # або make up-dev
```

Це свідоме рішення: файл із назвою `docker-compose.override.yml` підхоплювався
б автоматично й тихо перемкнув би робочий сервер у режим розробки.

## 5. Rate limiting

Redis, алгоритм «фіксоване вікно з лічильником» на ключ `rl:{scope}:{identity}:{window}`.

| Область | Ліміт за замовчуванням | Ключ | Поведінка без Redis |
|---|---|---|---|
| `login` | 10/хв | IP | fail-closed |
| `password` | 5/хв | IP | fail-closed |
| `enroll` | 20/год | IP | fail-closed |
| `device_auth` | 60/хв | IP | fail-closed |
| `key_rotation` | 5/год | device_id | fail-closed |
| `refresh` | 60/хв | user_id | fail-open |
| `upload` | 30/год | user_id | fail-open |
| `device_report` | 120/хв | device_id | fail-open |
| зміни стану | 120/хв | user_id / device_id | fail-open |
| читання | 300/хв | user_id / device_id | fail-open |

Ліміт застосовується до **всього** `api_router`, а не до окремих ендпоїнтів:
інакше кожен новий маршрут доводилося б не забути обмежити вручну. Читання й
зміни рахуються окремими кошиками — панель багато опитує, і спільний ліміт
довелося б робити настільки широким, що він перестав би стримувати зміни.

Ключ — суб'єкт токена, а не лише IP: офіс за одним NAT не ділить спільний
кошик, а вкрадений токен не обходить ліміт зміною вихідної адреси.

При перевищенні — `429` з `Retry-After`. Периметровий ліміт (30 r/s, 1 r/s
для входу) додатково стоїть у nginx, щоб очевидний флуд не доходив до Python.

## 6. Валідація введення

- Уся вхідна структура — Pydantic v2 з жорсткими типами й межами.
- **Тіло запиту**: `RequestGuardMiddleware` перевіряє `Content-Type` і
  `Content-Length` до того, як запит побачить застосунок.
- **Шляхи файлів**: нормалізація, заборона `..`, керуючих символів,
  зворотних слешів, **метасимволів оболонки** (`" ' \` $ ; & | < > ( ) [ ] { } * ? ! # ~`)
  і символів керування напрямком тексту; перевірка, що результат є нащадком
  одного із записів `file_roots` для цього пристрою. Порожній allowlist =
  файловий модуль вимкнений.

  Метасимволи заборонені саме тому, що шлях їде на пристрій і в каталогах
  з `allow_privileged` виконується через `su`. Агент перевіряє це повторно
  й екранує аргументи (`shellQuote`), а перелік дозволених утиліт
  фіксований — три незалежні рубежі замість одного.
- **APK**: magic-байти ZIP, стеля розміру, кількості записів і коефіцієнта
  стиснення (захист від «zip-бомби»), відхилення записів з абсолютними
  шляхами та `..`, SHA-256, розбір `AndroidManifest`. Непідписані пакети
  відхиляються; `APK_ALLOWED_SIGNERS` дозволяє закріпити власний сертифікат
  збірки.
- **Ідентифікатори**: UUID, ніяких «сирих» рядків у SQL — лише параметризовані
  запити SQLAlchemy.

## 7. Поводження з секретами

- Секрети лише з оточення (`.env`, Docker secrets, systemd credentials).
- `.env` у `.gitignore`; у репозиторії тільки `.env.example` із заглушками.
- У production сервер **відмовляється стартувати**, якщо `JWT_SECRET` /
  `TOKEN_HASH_SECRET` коротші за 32 символи або дорівнюють дефолтним.
- Секрети ніколи не потрапляють у логи: логер має список полів для маскування
  (`password`, `token`, `signature`, `authorization`, `secret`, `public_key`).
- Bootstrap-адміністратор створюється лише якщо таблиця `users` порожня.
- У production `Settings` додатково відмовляє старт, якщо: `JWT_SECRET`
  дорівнює `TOKEN_HASH_SECRET`; `PUBLIC_BASE_URL` або джерела CORS на http;
  `CORS_ORIGINS`/`ALLOWED_HOSTS` містять `*` або порожні; у `REDIS_URL` чи
  DSN бази стоїть дефолтний пароль.

### 7.1 Ротація серверних секретів

Обидва секрети мають «попереднє» значення на час переходу: підписуємо новим,
приймаємо й старе.

```
1) JWT_SECRET_PREVIOUS=<старий>, JWT_SECRET=<новий>  → перезапуск
2) зачекати повний REFRESH_TOKEN_TTL_SECONDS (типово 14 днів)
3) прибрати JWT_SECRET_PREVIOUS                       → перезапуск
```

Те саме для `TOKEN_HASH_SECRET` — але орієнтир очікування там довший із
refresh- та enrollment-TTL, бо цим ключем шукаються збережені хеші токенів.

`TOKEN_EPOCH=<ISO-8601>` відкликає **всі** видані токени одразу — на випадок
підозри на компрометацію ключа.

Поточний стан і процедура: `GET /api/v1/maintenance/secrets` (дозвіл
`secret:rotate`). Самих секретів ендпоїнт не повертає й повертати не може —
це перевіряється тестом.

### 7.2 Права в базі даних

Схемою володіє роль `POSTGRES_USER` — під нею виконуються **лише** міграції
(`MIGRATION_DATABASE_URL` в `entrypoint.sh`). Застосунок працює роллю
`POSTGRES_APP_USER` з `SELECT/INSERT/UPDATE/DELETE` і без права створювати
об'єкти чи змінювати схему: помилка в коді не перетворюється на `DROP TABLE`.
Роль створюється `infra/postgres/init/01-app-role.sh` при першій ініціалізації.

## 8. Аудит

Незмінний журнал `audit_log` (лише `INSERT`; у production рекомендовано
`REVOKE UPDATE, DELETE` на таблицю для ролі застосунку).

Фіксуються щонайменше:

`AUTH_LOGIN`, `AUTH_LOGIN_FAILED`, `AUTH_LOGOUT`, `AUTH_REFRESH`,
`AUTH_REFRESH_REUSE`, `USER_CREATED`, `USER_UPDATED`, `USER_DELETED`,
`ENROLLMENT_TOKEN_CREATED`, `ENROLLMENT_TOKEN_REVOKED`, `DEVICE_ENROLLED`,
`DEVICE_ENROLL_FAILED`, `DEVICE_UPDATED`, `DEVICE_DELETED`, `DEVICE_REBOOT`,
`DEVICE_SYNC_CONFIG`, `DEVICE_REFRESH_TELEMETRY`, `POLICY_APPLIED`,
`APP_INSTALL`, `APP_UPDATE`, `APP_UNINSTALL`, `APP_LAUNCH`, `APK_UPLOADED`,
`FILE_LIST`, `FILE_UPLOAD`, `FILE_DOWNLOAD`, `FILE_RENAME`, `FILE_DELETE`,
`FILE_ROOT_CHANGED`, `LOCATION_CONFIG_CHANGED`, `LOCATION_DISABLED`,
`REMOTE_SESSION_REQUESTED`, `REMOTE_SESSION_CONSENT`, `REMOTE_SESSION_STARTED`,
`REMOTE_SESSION_ENDED`.

Додано за підсумками аудиту:

`AUTH_PASSWORD_CHANGE_FAILED`, `AUTH_PASSWORD_RESET`, `AUTH_SESSIONS_REVOKED`,
`DEVICE_KEY_ROTATED`, `DEVICE_KEY_ROTATION_FAILED`,
`DEVICE_KEY_ROTATION_REQUIRED`, `DEVICE_TOKENS_REVOKED`,
`SECRET_ROTATION_VIEWED`, `SECRET_ROTATION_STAGED`, `ACCESS_DENIED`.

Кожен запис: час, актор (user/device/system), IP, user-agent, об'єкт,
результат (`success` / `failure` / `denied`), деталі (JSONB без секретів).

## 9. Що вважається інцидентом

- `AUTH_REFRESH_REUSE` — ознака викраденого refresh-токена; родина відкликається автоматично.
- Невдалий підпис пристрою кілька разів поспіль — можлива підміна `device_id`.
- Enrollment з IP поза очікуваним діапазоном — перевірити токен.
- Спроба доступу до файлу поза allowlist — записується як `denied` з повним шляхом.
- `FILE_ACCESS_DENIED` з причиною про символи оболонки — це не помилка
  оператора, а спроба ін'єкції: шлях із такими символами не може виникнути
  при нормальній роботі панелі.
- `DEVICE_KEY_ROTATION_FAILED` з `reason=bad_signature` — хтось має токен
  пристрою, але не має його ключа.
- Серія `ACCESS_DENIED` від одного облікового запису — розвідка прав.
